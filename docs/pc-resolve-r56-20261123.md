## wait_event 与等待原语

源为本机 enuma XNU 构建树 `.cache/xnu-work`（相对路径如下）；线程状态/事件在锁下取，但 user PCB 读是独立 relaxed load，见 `package/EnumaThreadSnapshot56.c:33-52,82-96`，故 PC 不保证指示当前内核等待调用栈。

* **零事件与 Mach 接收一致，不需假设异常**：`osfmk/ipc/ipc_mqueue.h:132` 定义 `IPC_MQUEUE_RECEIVE = NO_EVENT64`，`osfmk/kern/kern_types.h:80` 定义后者为 0；`osfmk/ipc/ipc_mqueue.c:1097-1119` 的 receive 使用此事件进 `waitq_assert_wait64_locked`，`osfmk/kern/waitq.c:568-570` 将 event 存入 `thread->wait_event`、将 waitq 另存到 `thread->waitq`。`ipc_mqueue.c:936-957` 有 receive 后阻塞路径。PC 位于 `mach_msg2_trap` 且 LR 在其调用者，强烈支持消息接收等待；但未取 syscall 参数、内核栈或 queue，因此收还是其他 mach_msg2 操作不能仅凭快照定论。零值还可由 `waitq.c:573-593` 清除事件后等待唤醒的过渡产生（此路径设置 TH_WAKING，不能直接套用本次精确 `st=1`）；单独 continuation 或 `thread_block` 不是零事件的充分证明。
* **非零事件与 worker park 一致，不是 IPC receive event**：`bsd/kern/syscalls.master:549` 定义 368 (`0x170`) 为 workq_kernreturn；`bsd/pthread/pthread_workqueue.c:3342-3437` workq thread return 后选择任务或 park，`:3691-3697` 对 `workq_parked_wait_event(uth)` 调 `assert_wait` 并 `thread_block`；`:284-287` 将事件定义为 `&uth->uu_workq_stackaddr`。这与 syscall stub、TH_WAIT 和两个不同非零 KVA 高度一致，但未读 syscall options/内核栈或 `uth`，不证明实际必经此路径。
* 非零 `we` 是 **event key，不是 thread->waitq 指针**；两个值不同只能证明 event key 不同，不能仅凭数值断言两个 waitq 对象不同或同一对象的不同元素。若实际走上述 worker park，则每个 key 是各自 uthread 的字段地址；这是路径条件下的推论。需采线程 `thread->waitq`、block hint、内核栈/continuation 以及关联的 uthread/port 类型才能归属；裸地址无法推出 IPC 对象归属。

## 可能场景（排序）

1. **Mach 消息接收 + 空闲 workqueue worker**（较强）：每进程各一条 trap/零事件及一条 workq/非零事件，与各自 XNU 路径一致；不能说明收的是哪个端口、等待消息为何未到、是否死锁或 GUI 初始化是否成功。
2. **进程暂时闲置或等待外部服务/事件**（中等）：同样解释两线程睡眠及一致的公共库地址；单次采样不能区分正常 idle 和永久停滞，也不能判断线程是否稍后被唤醒。
3. **陈旧或非原子 saved user state 与当前等待不同步**（必须保留）：可解释 PC/LR 与真实内核等待关系不符，尤其 SiriTTS LR；不能仅据此否定其他线程的实际等待。

最小额外观测：分别记录两进程各线程 `thread->waitq`、block hint 和内核栈/continuation，配合第二时点；独立核实 SpringBoard 自身 slide、Mach receive 端口身份。此处无新设备动作、无 build；不提升阶段。
