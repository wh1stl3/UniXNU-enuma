# v12：补齐 DISP_CC 映射，继续真实 OEM 启动链

2026-10-28，用户在本机异常归因和公开配置对照后明确“可以开始制作v12了”。该请求批准本轮制作所述范围的映射修复、新资格与完整镜像；本轮不启动设备，不沿用v11拍摄就绪。

## 范围和依据

只对新 scope `oem-exception-dispcc-v12` 应用 `display-dispcc-map.patch`，增加 `DISP_CC` 的0x0af00000/0x20000设备映射，属性为AddDev/MMAP_IO/UNCACHEABLE/MmIO/NS_DEVICE。不改变board.toml或bringup-plan的RAM字段、保留区、verified或分区。原厂DisplayDxe、ClockDxe、HAL IOMMU、真实Core返回和GOP门控保持；异常仍输出E11/E12/E13，采用新session和单次trial。

主证据为v11的ClockDxe+0x11d58读取0x0af022c0、ESR0x96000007与本机FDT范围，详见[故障分析](2026-10-28-oem-clock-fault-analysis.md)。映射建立发生在SEC的MemoryInitPei：GetMemoryMap→ValidateMemoryMap→逐描述符构造同址PhysicalBase/VirtualBase及属性→ArmConfigureMmu。AddDev不会命中HobOnlyNoCacheSetting跳过分支。

公开依据：

- [Qualcomm Kona DTS](https://android.googlesource.com/kernel/msm/+/bd6e2552761783ff60692d477767eddb556dd0ed/arch/arm64/boot/dts/qcom/kona.dtsi)：同基址/0x20000，配置总线GCC_DISP_AHB_CLK、MMCX供电。
- [Mu-Silicium j706f固定版本](https://github.com/Project-Silicium/Mu-Silicium/blob/4cba43c90e02cdbefbcd9fcdbda33d2328deaec0/Platforms/Lenovo/j706fPkg/Library/MemoryMapLib/MemoryMapLib.c)：相同范围及设备属性写法，不复制其他板的整体内存图。
- [edk2-msm SM8150固定版本](https://github.com/edk2-porting/edk2-msm/blob/e1952621f419f8db60ed28271264e1b5184c571d/Silicon/Qualcomm/sm8150/Library/PlatformMemoryMapLib/PlatformMemoryMapLib.c)：同类显式映射；跨SoC只参考形式。
- [官网平台适配流程](https://unixnu.com/porting/platform)：本轮重新读取，按本机MMIO来源、缓存属性、实际固件映射核对，软件与硬件验收分开。

备选A为仅映射故障页0x0af02000/0x1000，改动更窄但容易在同一控制器下一寄存器再次异常；备选B为按本机FDT映射整个0x20000控制器窗口。采用用户已知并批准制作的B，避免任意扩大为整个外设地址空间。仍不保证电源、访问权限或时钟握手通过。

## 新故障与进度

- PC 0x9a6ff140，ESR 0x96000047，FAR 0x0aeb0004，LR 0x9a6ff120。
- E12唯一归属：base 0x9a6d4000，RVA 0x2b140，size 0x4d000；E13 GUID 4138022f-06c7-4f79-9c94-7e33b511a4e7，与本FD原厂DisplayDxe唯一匹配。
- 原PE摘要6c6351c3c770d4f698e5e22097021fe8d20d35a8d4181df05676a48c4347f425；实际指令0xb8154128，即 `stur w8,[x9,#-172]`。ESR为同EL data abort，WnR=1，DFSC=7（L3翻译故障），FnV=0；宽度由实际指令确定为32位。
- 本机FDT的mdss_mdp节点明确vbif_phys=0x0aeb0000/0x2008，故障为VBIF+4。构建映射Display MDP只到0x0ae85000，无描述符覆盖本次FAR。
- LR是本函数内BL到0x2b398后的位置；helper返回后才发生写故障。不能用这个LR声称构造器/GOP方法的上层调用阶段已经确定。

相较v11的ClockDxe+0x11d58读取DISP_CC故障，本轮实际到达原厂DisplayDxe的VBIF写操作，是推进证据；仍未证明OEM返回、完整DXE、生产GOP、ConOut或BDS成功。未采集实时页表，运行中修改仍不能彻底排除。
