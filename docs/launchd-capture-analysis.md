# launchd 捕获离线判读

只读 UTF-8 输入；不采集设备、不修改内核。复用 Python 标准库，无外部依赖。

```
python3 scripts/analyze_launchd_capture.py capture.txt --format serial
python3 scripts/analyze_launchd_capture.py frames.txt --format frames
```

录像输入每行 `帧号/真实秒数/该帧新增的一行原文`，同一帧多行分别写一行，保持屏幕出现顺序；不重复抄前帧仍留在屏幕上的行。帧号允许重复但不得倒退。串口每行一条原始日志。支持包含 `launchd` 或 `launchd[1]` 的行，服务形式 `name[pid]`（可带 `system/`、`user/501/` 域）或 `pid/5 [SpringBoard]`；启动识别 `Successfully spawned`、`state: running`、`SOURCE_ATTACH`，退出识别 `exited`。报告计数是匹配行数，不是启动次数。逐行核对未覆盖的实际格式，未识别不能当作未发生。

`--complete` 是操作者对**窗口连续、无漏行、顺序可靠、上述格式覆盖退出和启动行**的明确声明，不适用于摘要或掉帧；未声明时不能得出推进。显示时间戳只认行首 `[秒.小数]`，真实秒数仅作位置注释；两者均不参与结论。负跳单独报告，未发现负跳不表示时间可靠。

| 条件 | 结论 |
| --- | --- |
| 同名三个递增 pid 的启动，前两次各有匹配 pid 的退出且分别在下次启动之前 | respawn 环，仅指观察到的重复重启模式 |
| 声明完整捕获，至少三个不同服务的首次启动，未识别到退出行 | 推进，仅指窗口内新服务启动，不等于服务稳定 |
| 其他情况，包括存在退出但不足以确认重启链 | 无法判定，补连续启动及退出原文 |

输出还列出所有匹配的服务行、pid、递增位置、未唯一关联的退出、连续新服务段。窗口尾部或缺失记录均不能证明不再退出；混合推进和重启时，已确认的重启链优先输出。多服务共行的 exited 不猜关联。来源域不作为服务名的一部分；同名跨域需人工拆分捕获后复核，不能当作同一服务重启。

## r4 自测（self-checked）

```
python3 scripts/analyze_launchd_capture.py docs/ufs-launchd-data-20261119-observation.md --format serial
```

实际输出：

```
服务出现次数与 pid 序列（按匹配行）:
  无可识别服务行
exited:
  无
递增新 pid:
  无
连续新服务段（识别到的启动事件）:
  无
时间戳倒退:
  未发现（不代表时钟可靠）
结论: 无法判定（缺连续完整捕获及可关联服务名/pid 的启动、退出序列；不得将日志缺失视为未退出）
```

该文档是摘要而非逐行原始日志；未识别不是说屏幕没有这些行。与原文「早期启动成立、稳定与推进未成立」一致。合成样本自检覆盖两个退出及三个递增 pid、时间倒退、录像格式及完整性开关；尚无真实逐行日志格式验证。

工具不能证明服务持续存活、launchd 初始化完成、显示、持久化或时钟机制；结论受捕获完整性、格式识别和人工转录准确性限制。
