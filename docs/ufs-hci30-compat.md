# UFSHCI 3.0 applicability check for the 24r read set

2026-11-11. Host-only, read-only. **No device command, no runtime source change,
no change to the active gate (A: `VER == 0x210` only).** Self-checked unless an
independent verifier reruns it.

**Result: the 14-item evidence is not sufficient to admit a bounded 3.0 read
path. Keep A (refusal). B and C are not auto-admitted.**

## Why

24r reported `UFS_REUSE INCOMPLETE unsupported HC version`, `off=8
raw=00000300`. `UfsReuseAdmission.h:120-122` accepts only `0x210` and stops
before the remaining 13 HC reads. `0x300` decodes as UFSHCI 3.0 under the fixed
Linux version scheme (`ufshci.h:79-89`: `major << 8 + minor << 4`). This check
asks whether the board's controller version and
the vendor `BROKEN_UFS_HCI_VERSION` condition are known, and whether each
newly-reachable read has a per-item basis.

## Board vendor version and `BROKEN_UFS_HCI_VERSION` — UNKNOWN

Fixed-source condition: `ufs-qcom.c:833-834` sets
`UFSHCD_QUIRK_BROKEN_UFS_HCI_VERSION` only when `host->hw_ver.major == 0x2`.
`hw_ver` is parsed from vendor `REG_UFS_HW_VERSION = 0xE4`
(`ufs-qcom.h:43,133-141`); with the quirk,
`ufs_qcom_get_ufs_hci_version()` reports 2.0 (`ufs-qcom.c:799-807`), so
`ufshcd_get_ufs_version()` ignores the raw `0x300` (`ufshcd.c:705-723`).

Conclusion: this board's `hw_ver.major` and therefore whether Linux would apply
`BROKEN_UFS_HCI_VERSION` is **UNKNOWN**. A `0x300` reading is compatible with
either branch; it cannot be used to infer `hw_ver`. The `SM8250` name is not
used as proof. No `0xE4` read is added here or to any candidate.

## Reachability change of B (and C)

- **A (current):** 4 GCC + HC `VER` = 5 reads, two maps (GCC/HC), terminal
  `INCOMPLETE`; no SMMU map, no SMMU read, no second sample.
- **B:** accepting `0x300` makes the remaining 13 HC reads reachable, then 4
  SMMU globals (`0x0/0x20/0x24/0x28`), up to 128 SMR + 128 S2CR reads, then
  CBAR/CBA2R/SCTLR for the two candidate streams, then the **entire second
  sample** repeats (successful path total 568 reads) before
  `OBSERVED_REUSE_SHAPE`. That includes the six HC registers with no read
  evidence and the whole SMMU table/context path, which A never reaches.
- Default-off/read-set-unchanged limits the default build but **does not
  eliminate** this: any candidate built with B enabled gets the full path, and
  the code path itself is new and must be reviewed/tested. The 24r observation
  only evidences the first 5 reads; it says nothing about the other 13 HC reads
  or the SMMU path.
- **C** (only CAP/VER/HCS/HCE) reduces the read set but is still a new 3.0
  admission with the same unresolved board-quirk condition; it is not
  automatically admissible just because it reads fewer registers.

## Sufficiency and next minimum evidence

The 14 offsets and consumed bits are source-bound, and 8 of 14 have Linux
read-adoption evidence. That is **not sufficient** for any bounded next
implementation because:

1. board `hw_ver.major` / quirk applicability is UNKNOWN (above);
2. six newly-reachable HC reads have no read-side-effect evidence;
3. 3.0-only register deltas are UNKNOWN (JESD223D not available; the HTTP 402
   source was not requested again).

Keep A. The minimum new evidence, in order, is: (a) a board-specific binding
(static material, or a separately authorized read-only log) of the vendor
version or the Linux driver's applied `ufs_version`; none is present in the
checked live ADT, enumaPkg config, UFSDxe strings/disassembly, XBL strings, or
captured dmesg; (b) normative access/read-side-effect text for
`0x50/54/60/70/74/80` from JESD223C/D or a vendor document. Adding a `0xE4`
read is **not** proposed here and would require separate authorization. If the
owner chooses B without these, that is an explicit risk acceptance, not
evidence sufficiency.

## GCC / SMMU notes

GCC `0x77004/10/18/cc` semantics match v6.1 (`gcc-sm8250.c:3257-3263,2841-2874,
1090-1108`; `gdsc.c:20,59-93`; `clk-branch.c:42,47-64`); measured
`gdsc=0xf822f000 axi=0x221 ahb=0x1 aggr=0x1` passed those checks. The SMMU
layout is UFSHCI-version independent (`arm-smmu.h:27,45,59,65,100,105,123,140,
144`; `arm-smmu.c:1774-1783`) and was already part of the 2.1 candidate; B
changes its reachability, not its register map. No GCC/SMMU change is proposed.

## Verified vs unknown

- Verified (source read, line-cited): offsets/bits, v6.1 read/write call sites,
  the vendor quirk condition, SMMU/GCC layouts, board address windows, absence
  of a board version binding in the checked materials.
- Unknown: board `hw_ver.major`; read side effects of six HC registers; any
  JESD223D-only 3.0 delta; firmware-left HCS/HCE/queue state; all runtime.
- Not claimed: that 3.0 reads are safe, that the controller/queue/SMMU is
  quiescent, or that PMGR/stage23/AMFI passed.
